# treemapper-garmin

The native Connect IQ link, on **Android and iOS**.

It wraps `com.garmin.connectiq:ciq-companion-app-sdk` on Android and the
Connect IQ Mobile SDK for iOS, and exposes both to JavaScript as one Expo
module, `TreeMapperGarmin`. Everything above it lives in `src/garmin/`: the
protocol parser, the development mock, the transport interface this satisfies,
and the hook that drives a session.

Nothing here parses a message. Both native sides emit payloads raw and
`src/garmin/protocol.ts` interprets them, so the mock, the watch and the
handheld go through one parser and a wire format change has exactly one place
to be understood.

## Why a local module, and why a plugin beside it

`apps/mobile/android/` and `apps/mobile/ios/` are gitignored and regenerated by
`expo prebuild`, so a hand edit in either does not survive. Expo autolinking
picks up every package under `modules/` automatically, on both platforms:
`android/build.gradle` and `ios/TreeMapperGarmin.podspec` are found without
anything being registered.

Native **configuration** is never automatic, so it lives in `app.plugin.js`
here, named once from `app.json`. It writes the `<queries>` entry for Garmin
Connect into the Android manifest, and into Info.plist the `gcm-ciq` query
scheme, this app's own `treemapper-ciq` URL scheme, a Bluetooth usage string
and `CFBundleDisplayName`. Each of those fails quietly if missing, and the
Swift reads the URL scheme back out of Info.plist so the two cannot drift.

## The API

| Call | Android | iOS |
|---|---|---|
| `start(tethered?)` | `initialize()`, find a device, register listeners | attach, bind the remembered device, register listeners |
| `stop()` | unregister and `shutdown()` | unregister; the SDK stays initialised |
| `send({ c, ms? })` | `sendMessage()`, wrapped as a single-element list | `sendMessage(_:to:progress:completion:)`, same wrapper |
| `openWatchApp()` | `openApplication()` | `openAppRequest(_:completion:)` |
| `openStore()` | `openStore()` | `showConnectIQStore(for:)` |
| `chooseDevice()` | nothing | `showConnectIQDeviceSelection()` |

One event, `GarminLinkEvent`, carrying the union in `src/garmin/transport.ts`.

`send` takes a Record rather than a loose map so `ms` crosses the bridge as an
`Int`. The watch checks `ms instanceof Number` and Monkey C's `Number` is a
32-bit integer, so a JavaScript number arriving as a Double would be silently
ignored and the rate would never change.

## What differs on iOS, and why the phone has to care

The two SDKs disagree about who owns the Bluetooth link, and one of the
differences reaches all the way to the screen.

**Android routes everything through Garmin Connect Mobile.** iOS talks to the
device itself and needs GCM only to discover devices and to reach the store. So
there is no `ServiceUnavailableException` to translate on iOS, and no
`shutdown()`: `initialize` happens once per process in
`TreeMapperGarminAppDelegate` and lasts until the app dies.

**iOS cannot read the paired device list.** The only route is
`showConnectIQDeviceSelection()`, which launches Garmin Connect, backgrounds
TreeMapper, and answers by opening `treemapper-ciq://...` with the chosen
devices in the query string. That is a user-visible trip, so `GarminLink.swift`
persists the answer in `UserDefaults` and reuses it from then on. The blocker
`needs_device` is how the phone asks for the trip, and the modal's "Choose
device" button is what makes it. It is the one event Android never sends.

**The device list is authorisation, not a cache.** When GCM answers, the stored
list is replaced rather than merged. A device the user has just revoked must
not survive.

## The iOS SDK is vendored

`ios/vendor/ConnectIQ.xcframework`, with the release in `ios/vendor/SDK_VERSION`.

Garmin publishes it as a Swift package at
<https://github.com/garmin/connectiq-companion-app-sdk-ios>, which CocoaPods
cannot consume, and there is no pod for it. The xcframework is 1.7 MB and
checking it in keeps a fresh clone buildable offline, with no download step in
the middle of a prebuild. The podspec vendors it and adds the `-ObjC` linker
flag Garmin's guide asks for.

To move to a newer release: download that tag's `ConnectIQ.xcframework`,
replace the folder, update `SDK_VERSION`, and read the headers in
`ConnectIQ.framework/Headers/` before trusting any method name. They have
changed between versions and the published documentation lags behind them.

## Testing without a Garmin in the room

**Android, with the Connect IQ simulator.** It bypasses Garmin Connect entirely
and speaks to the simulator over an ADB-forwarded socket. A release build
ignores the flag, so this cannot reach a user, and iOS ignores it too: there is
no simulator transport in that SDK.

```js
import { setGarminTetheredMode } from 'src/garmin'
setGarminTetheredMode(true)
```

Then, in this order, because the phone has to be holding the socket open before
the simulator dials in:

1. `adb forward tcp:7381 tcp:7381`
2. run the watch app in the Connect IQ simulator
3. open a TreeMapper capture screen and press the Garmin button
4. Connection > Start in the simulator

Two things behave differently over ADB and are handled rather than fixed,
because they are the simulator's doing and not ours. The SDK reports the device
as `UNKNOWN` and never promotes it to `CONNECTED`, and `getApplicationInfo`
answers "not installed" even while the app is plainly running. Both are
advisory over this transport, so the listeners are registered anyway and the
messages are allowed to settle it.

The third is the one that bites. The simulator stamps its outbound messages
with an **empty** application id rather than the id in `manifest.xml`, and the
SDK routes inbound messages by that id. So this module registers for the empty
id on TETHERED and the real id on WIRELESS, one each and never both: the SDK
keys a registration per device, so a second call replaces the first rather than
adding to it, and an arriving message with no handler takes the SDK's reader
thread down with it.

**iOS has no equivalent.** A real device and a real iPhone are the only way to
exercise `GarminLink.swift`: the iOS Simulator has no Bluetooth and Garmin
Connect is not installed there. For the flow rather than the link, the mock
transport in `src/garmin/mockTransport.ts` has a `needs_device` scenario that
imitates the Garmin Connect round trip, including the wait.

## On a fresh clone

Nothing here needs a manual step. That is the whole point of it being a module
rather than an edit to `android/` or `ios/`, both of which are gitignored and
rewritten by every `expo prebuild`.

```bash
nvm use                 # node 22, per .nvmrc
yarn install            # at the repo root: this is a yarn workspace
cp apps/mobile/.env.sample apps/mobile/.env

cd apps/mobile
npx expo prebuild --platform android --clean
npx expo prebuild --platform ios --clean      # runs pod install for you
```

Then `npx expo run:android --device` or `npx expo run:ios --device` as usual.

**Verify the module was picked up**, without waiting for a build:

```bash
cd apps/mobile
npx expo-modules-autolinking search -p android | grep treemapper-garmin
npx expo-modules-autolinking search -p apple   | grep treemapper-garmin
```

Each should print the path to this folder. Autolinking walks `modules/` on its
own, so there is nothing to register.

**What a new developer does NOT have to do:**

- No download from Garmin's developer portal. The iOS framework is committed
  under `ios/vendor/`, about 1.7 MB, and a clean clone builds offline.
- No Maven setup. The Android AAR resolves from Maven Central, which is already
  in the repositories of the generated `android/build.gradle`.
- No Info.plist or AndroidManifest edit. `app.plugin.js` writes every one of
  those at prebuild time, and `app.json` already names it.
- No Xcode project surgery. The podspec is found by autolinking.

### If something is missing after a prebuild

- **The module did not autolink.** Run the two search commands above. An empty
  result on Apple usually means `ios/vendor/ConnectIQ.xcframework` did not come
  down with the clone: check it with `git ls-files | grep xcframework | wc -l`,
  which should print 76, not 0.
- **Android fails with `package com.<something> does not exist`.** That is the
  stale autolinking cache described in the root `CLAUDE.md`, not this module.
  `rm -rf android/build/generated/autolinking android/app/build/generated/autolinking`
  and rebuild. `prebuild --clean` does not fix it.
- **The Garmin button does not appear on a device build.** The native module is
  absent, so `hasNativeGarminLink()` is false. In a debug build the mock stands
  in, which is why the button can be there in development and gone on a real
  phone.

## Build one piece at a time

```bash
# Android: just this module
cd apps/mobile/android && ./gradlew :treemapper-garmin:assembleDebug

# iOS: regenerate the project, then let the pod pick the module up
cd apps/mobile && npx expo prebuild --platform ios && cd ios && pod install
```
